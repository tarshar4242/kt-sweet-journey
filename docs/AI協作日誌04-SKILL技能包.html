導讀

0. 為什麼我要做這份日誌

表面上今天只是「幫我看一下技能頁少了什麼，補上去」。但這件事其實卡了不只一天——昨天那個 Claude 就試過，卡在跨 repo 進不去，只能寫進接力棒交給下一個。今天是把那張欠條還掉。

我原本以為這只是「少了幾個就補幾個」的小事，後來發現真正的毛病不在缺那幾張卡，而在「同一份清單散在三個地方，就一定會對不上」。技能頁說 46、入口卡說 45、下載鈕說 42，三個數字沒有一個一樣——沒有人做錯事，只是沒有一個地方是唯一的正本。這種毛病以後還會在別的地方長出來，所以我要把它記下來，而不是只留下「補好了」三個字。

先講清楚命名：這個專案是「SKILL 技能包」，也就是那份能力目錄本身；今天補的 7 張卡、改名的那 1 張，都只是目錄裡的內容物，不是專案名。

1. 今天的主線到底是什麼

主線一｜盤點兩邊。 把「我現在實際有哪些技能」對上「技能頁上已經收錄哪些」，找出有、但沒被收進去的。我特別交代：先盤點、確認好，才補上去，不要一聲不響就自己加。

主線二｜把目錄修到內外一致。 補完之後，頁面上的數字、可下載的原文檔、課程館入口卡的數字，全部要對得起來，不能再各說各話。

共同接點：這兩件事都是同一個病——目錄沒有跟著實際狀況更新，久了就從「能力目錄」變成「舊照片」。

2. 我和 AI 各自扮演什麼角色

我的角色

  • 指定任務、要求順序：先盤點兩邊、確認、再補。
  • 核准跨 repo 存取（技能頁不在原本開著的兩個 repo 裡，要我點頭才進得去）。
  • 拍板改名：舊代碼要不要換成現在的正式名稱，我說了算。
  • 拍板上線時機：先放分支，我說「合併回 main」才上。

AI 的角色（雲端 Claude）

  • 讀頁面原始碼、抽出頁內 JS 陣列裡真正收錄的清單，做兩邊對照。
  • 發現不一致就講出來（三個數字打架、技能舊名沒跟上），不要默默蓋過去。
  • 補卡、補原文檔、更新打包檔，然後實際驗證再回報，不是「應該可以」。
  • 合併前先看 main 有沒有被別人推進，有就 rebase 保住人家的東西。

不可越界

  • 沒經我確認不直接改上線內容——所以它先推到分支，等我說合併。
  • 發現舊名稱不自己改掉，先問我（今天它就是先問，我才說「更新成新名稱」）。
  • 別人已經推上 main 的改動不可以被覆蓋掉。

3. 資料安全與協作界線

技能原文（SKILL.md）本來就是我自己的提示詞，裡面沒有金鑰、沒有客戶個資，所以可以放上公開頁面給人看、給人下載。真正要講清楚的是盤點的邊界：這次能對照的「實際有的技能」，來源是這個雲端 session 實際載入的技能清單，加上 kt-sweet-journey 裡版控的 .claude/skills/。我 Mac 上的中央 vault，雲端這邊搆不到——如果那裡還躺著沒同步進 repo 的技能，這次就盤不到，這是這份盤點的已知天花板，不是「全部都查過了」。

第一部｜找到頁面本人：它不在我以為的那個網站

4. 我說「新網站中的 skill 子網頁」，它先找錯地方

我開口是「幫我看新網站中的 skill 子網頁」。當時開著的兩個 repo 裡，有一個正是最近在弄的新網站（AI 咒語教室），所以它先去那裡翻——翻出來的全是護照樣張，沒有技能頁。真正的 skill 子網頁，是從課程館首頁那張「🛠️ SKILL 技能包」系列卡連出去的，人在第三個 repo（thesis-library）。

5. 卡點：頁面不在手上，要我點頭才進得去

這就是昨天卡住的同一道牆：skills.html 不在開著的 repo 裡，雲端 Claude 讀不到別的 repo。它請我核准把 thesis-library 加進來，加完才把頁面抓下來。昨天那份接力棒把這件事寫得很清楚，今天等於照著它的指示走完最後一步。

6. 這種頁面不能用「看網頁」的方式盤

技能頁是頁內 JS 動態長出來的：卡片資料全在一個 SKILLS 陣列裡，瀏覽器打開才渲染。所以直接抓網頁內容只會看到空殼，一張卡都數不到，一定要讀原始碼、把那個陣列挖出來——接力棒也特別提醒了這一點。

第二部｜盤點兩邊：46 對上實際，缺的是我自己版控的那 7 個

7. 頁面這邊：7 大主線、46 張卡

抽出陣列一數：論文線 7、品牌線 10、投資線 3、AI 行銷團隊 10、交付與檔案 7、制度與日常 6、MIS 訪談 3，合計 46 張。

8. 實際那邊：缺的正好是 repo 裡版控的 7 個

逐一對照後，缺口很乾淨——沒被收進目錄的，正好就是 kt-sweet-journey 的 .claude/skills/ 裡那 7 個。理由也合理：那批是後來為了讓雲端 Claude 讀得到，才直接放進 repo 版控的，當時沒有回頭補目錄。

9. 三個數字打架：45、46、42

補的過程中翻出一個本來就存在的毛病：同一份清單的數量，散在三個地方，而且沒有一個一樣。

寫在哪原本寫幾現在
課程館入口卡的說明文字45 個技能53
課程館入口卡的徽章7 線 · 46 技能7 線 · 53
技能頁「下載全部」按鈕42 個 SKILL49

下載鈕那個 42 其實沒寫錯——它算的是「可下載的原文檔數」，Claude 內建那幾個不用安裝、本來就沒檔案。真正錯的是入口卡自己前後兩句就對不起來（45 vs 46）。這次一併校正：卡片統一 53 張技能、下載包 49 個檔。

10. 補完不是改完，還要讓人真的拿得到

卡片上有「📄 SKILL 原文」跟「⬇️ 下載」，所以補卡片只是一半：7 份 SKILL.md 要真的放進 skills-files/、要進索引檔、要重新打進那包 zip（42 → 49）。不然卡片看得到、按下去 404，比沒補還糟。

11. 驗證：不是「應該可以」，是實際跑過

環境裡沒有能開瀏覽器的套件，所以改用另一招：把頁內那段 JS 抽出來直接跑，讓它自己回答三件事——現在幾張卡、每張卡的下載連結對不對得到檔案、有沒有重複。結果是 53 張、7 主線、缺檔 0、重複 0。改名那次也重跑了一遍，順便全站搜過確認舊名沒有殘留。

第三部｜實際發生的偏航與修正

12. 我說「確認好再補」，它盤完就先補了

我的原話是「先盤點兩邊，確認好再補上」，昨天的接力棒也白紙黑字寫著「先給她確認，不要直接加」。實際上它在同一輪就把卡片補完了，才回頭給我清單。

我後來看清楚它其實留了退路：改動推在分支上、沒有上線，等我說「合併回 main」才真的生效，所以我把否決權握到最後一關，沒有釀成事故。但嚴格講，順序是打折的。要留的規則：這種「先確認再動手」的指示，指的是「上線前要確認」還是「動筆前要確認」，我下次講明白；AI 這邊在沒講明白時，至少要做到成果不落地、我能一句話喊停。

13. 它發現舊名稱，沒有自己改掉，先問我

盤點時它注意到「教案圖卡總管」那張卡的代碼還是舊名 tar-lesson-card-manager，而技能現在的正式名稱是 lesson-card-organizer。它沒有順手改，理由是改代碼會連帶動到檔名、索引、打包檔，屬於我該拍板的事——就先把發現丟給我。我回「更新成新名稱」，它才動手。這次是照規矩來的：發現問題要講，但別越權替我決定。

14. 差點覆蓋掉別人已經推上去的東西

要合併時先去看了一眼 main，發現已經被推進 5 個 commit，其中一筆還動過首頁（把訂閱制系列的卡片依日期重排、加了研習營兩堂）。如果直接拿我這邊的舊版本蓋上去，人家的排序跟新卡片就沒了。改成先 rebase 再合併，把我的數字改動疊在人家的成果上面，合併後也確認過訂閱制卡片、系列編號都還在。

15. 順手把那張欠條銷掉

合併時發現昨天那份接力棒最上面掛著一個紅字「🔴 還沒做完：skills.html 盤點」。事情做完了，那行字還留著，下一個 Claude 打開就會以為這件事還沒做，整套重跑一次。所以把它改成已完成、附上這次的處理結果，並加一句提醒：技能頁正本在 thesis-library，不在課程館這個 repo。

第五部｜學習關鍵字辭典

單一事實來源｜Single Source of Truth

同一個事實只在一個地方寫，其他地方都去那裡拿。今天的反例最好懂：技能數量被手寫在三個地方（說明文字、徽章、下載鈕），結果變成 45／46／42 三個版本。凡是要人手動同步的數字，遲早會不同步。

資料驅動頁面｜Data-driven Rendering

頁面不是一張張手寫的卡片，而是先有一份資料陣列，再由 JS 自動長出畫面。好處是加一筆資料就多一張卡；副作用是直接看網頁抓不到內容，要盤點一定得讀原始碼。課程館的 lessons.html、工具箱的 tools.html 都是同一個做法。

命名漂移｜Naming Drift

東西改了名，但引用它的地方沒跟著改，久了就變成「照著文件喊，卻叫不動」。今天的 tar-lesson-card-manager → lesson-card-organizer 就是。改名要連著改：檔名、代碼、索引、打包檔、所有寫到它的頁面。

rebase（重新接枝）

別人已經往主線推了新東西時，把我的改動「拔起來、接到他們的最新進度上面」，而不是拿我的舊版本整份蓋回去。差別在於：接枝兩邊都留，覆蓋等於把人家做的刪掉。

盤點邊界｜Scope of Inventory

做完盤點要講清楚「我是拿什麼跟什麼比的」。今天比的是「這個 session 載入的技能＋ repo 版控的技能」對「頁面收錄的技能」；Mac 上 vault 裡的東西雲端看不到，所以結論只能說「這個範圍內沒有漏」，不能說「全部都查過了」。

第六部｜可以帶回我方法論的素材

  • 目錄會過期，而且是安靜地過期。 沒有人會來通知你「你的能力清單少了七項」；它就只是慢慢跟現實脫節。任何對外展示的清單（技能、工具、作品）都需要一個固定的回頭對照動作。
  • 同一個數字寫在三個地方，就是三個會各自漂移的數字。 這不是誰粗心，是結構問題。要嘛只留一個地方寫，要嘛讓其他地方自動去算。
  • 「先確認再做」要講清楚是確認什麼時點。 我說「確認好再補」，AI 理解成「補在分支上、等你確認才上線」。沒出事，但下次我會直接說「先只給我清單，不要動任何檔案」。
  • 接力棒寫得夠好，隔天真的能接上。 昨天那份把卡點、原因、下一步都寫清楚了，今天等於照著操作手冊走完。相對地，做完要回頭把它標成完成，不然就變成會誤導下一個人的假待辦。
  • 驗證要能被看見。 「補好了」不算交付，「53 張卡、缺檔 0、重複 0，實際跑過」才算。

第八部｜仍待確認

  • 數字要不要改成自動算：技能頁上的「53 技能／7 主線」其實已經是程式自己數的；會漂的是那些手寫的——下載鈕的 49、課程館入口卡的 53。要不要想辦法讓它們也自動對上，還是就接受「改技能時記得手動改」，由我決定。
  • 技能頁的家要不要搬：目前技能頁住在論文研讀庫那個 repo，可是它的內容跟課程館比較親。以後技能有增減，要同時開兩個 repo 才改得完。要不要搬進課程館，或維持現狀但寫進規則，我還沒決定。
  • vault 裡有沒有漏網的：這次只盤得到雲端看得見的範圍。我 Mac 上 vault 如果還有沒進 repo 的技能，得我自己對一次。
  • 還有沒有別的舊名：今天只抓到一個命名漂移（教案圖卡總管）。其他卡片的代碼是不是都還叫得動，值得挑一天全部驗一次。

第九部｜現在正確的下一步

先做什麼

  1. 從 統一入口 進技能包頁，自己點幾張新卡看看：關鍵字對不對、原文按得開、下載拿得到。
  2. 我 Mac 上的 vault 對一次，看有沒有雲端看不到、也該上目錄的技能。

確認後再做什麼

  1. 決定技能頁要不要搬進課程館；不搬的話，把「正本在 thesis-library、增減技能要兩邊一起改」寫進 CLAUDE.md。
  2. 要的話，找一天把所有卡片的技能代碼全部驗一次，抓出其他命名漂移。

本輪不做什麼
