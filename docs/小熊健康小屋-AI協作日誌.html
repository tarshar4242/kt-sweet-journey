0. 為什麼我要先做這份日誌

先生看診確認糖尿病初期，並持續服用高血壓藥。我想做的不是只有「先生一個人改」，而是整個家庭作息與飲食一起調整，最後做成一個兩人都能用的網頁工具。這件事前後經過十幾輪討論與修改，最後做出「小熊健康小屋」並且正式上線。

我後來確認，不能只留下最後那個網站。真正值得留下的是：

  • 我原本怎麼想。
  • AI 一開始怎麼理解。
  • 哪裡偏離了我真正要的。
  • 我怎麼把它拉回來。
  • 我們因此形成什麼新做法。
  • 哪些觀念可以帶回我自己的研究。
  • 哪些規則值得在下一次協作直接沿用。

要先說明一個跟固定順序不同的地方：這次不是「先寫日誌、確認後才動工」，而是先把工具整套做出來、上線、用過幾輪之後，我才回頭要求補這份日誌與學習日誌。順序雖然反過來，但整理方式一樣：逐段還原真實發生的事，不美化、也不事後合理化。

1. 這次協作的主線到底是什麼

這次的核心不是先做一個網站，而是先想清楚一件事：一個外食為主、午晚餐在公司吃、菜色不能選的家庭，怎麼把糖尿病初期與高血壓的生活調整落地成兩人都做得到的日常。

主題一｜家庭生活調整方案本身

決定：

  • 哪些餐次是真正可控的（早餐、宵夜、週末）。
  • 公司午晚餐這種半可控的餐，可以動哪三招（順序、份量、醬料）。
  • 運動、睡眠、監測、用藥、夫妻共同機制各自要顧到什麼。

主題二｜把方案變成兩人都會打開的工具

決定：

  • 要不要互動、要不要看得到對方。
  • 先生是 3C 不熟悉的使用者，操作要多簡單。
  • 資料要不要留得住、能不能拿去給醫生看。
  • 怎麼讓兩人願意持續打開這個網頁，而不是三天新鮮感過了就沒人用。

兩條主線的共同接點

工具是方案的載體，不是先做工具再找內容塞進去。方案本身有沒有想清楚，決定了工具功能設計得對不對。

七大生活面向（先討論方向）
→ 早餐／宵夜／週末優先落地成具體公式
→ 確認雙人互通與角色設定（一二娟／布布龍）
→ 做出第一版工具並端對端測試
→ 逐輪迭代：互動 → 資料保存 → 獎勵 → 介面收斂 → 日曆
→ 每輪都先在工作分支交付、確認後才合併上線

2. 我和 AI 各自扮演什麼角色

我的角色

我提供真實的家庭情境，不是空泛地說「幫我做一個健康 App」。

我負責：

  • 提供先生的診斷狀況、兩人的外食限制與生活現況。
  • 對每一版介面或功能給出直覺反應（喜歡、不喜歡、忽略掉了）。
  • 指出哪裡不符合我們家真正的樣子（例如：風格要走小熊路線、要能互相看到對方吃了什麼）。
  • 決定什麼時候可以正式上線。

AI 的角色

AI 不是代替我決定我們家要怎麼生活，而是：

  • 把口語描述的需求翻譯成具體可執行的公式與功能規格。
  • 在動工前先做技術風險判斷（例如同步機制怎麼選、顏色要不要驗證）。
  • 每次改版都先自己測試過一輪，而不是交出去讓我第一個發現錯誤。
  • 保存每一輪的決策與待辦，不用我自己去記。

今天形成的協作原則

我負責家庭生活的真實情境與感受判斷，AI 負責把需求轉成規格、做風險判斷與測試；AI 可以主動做技術決定，但介面和功能好不好用的拍板權在我，而且沒有我明確說「上線」「完工」之類的話，不能自己把東西公開發佈。

3. 專案與協作的底層安排

這不是多方協作案，只有我和 Claude 兩方。沒有 Codex、沒有業主、也沒有正式的 Pull Request 審核流程——這是我自己的家庭專案，沒有第二個人要審核。

取代 PR 審核的把關方式

今天釐清的是：因為沒有其他人可以審核，把關方式改成「工作分支 + 我明確同意才合併」：

  • 每次改版都先推到獨立的工作分支，不直接動 main。
  • 我看過預覽、講出「上線」「完工」這類明確的話，AI 才把工作分支合併進 main、推上 GitHub Pages。
  • GitHub 上的 main 分支，就是這個專案唯一的正式版本（單一事實來源）。

這次觀察到的落差

第一次合併確實有先取得我的明確同意；但從第二輪功能開始，AI 把「我曾經同意上線」延伸解讀成之後每一版做完都可以直接合併、只回報「上線了」，沒有每次都重新問我一次。這件事我目前沒有反對，但這是 AI 自己延伸出來的默契，不是我每次都重新答應的——這點放進第三部的偏航紀錄裡誠實記著。

4. 資料安全與家人隱私原則

這次的資料比一般專案更敏感：先生的血壓、體重、三餐內容，都是實際的健康紀錄。

最適合的說法

不需要把資料放上任何公開或商業的雲端資料庫，本機儲存＋兩人自己傳連結就夠用；哪天真的想要更即時的同步，再另外評估要不要接雲端服務，那是全新的決定，不是現在的預設。

這次採用的資料揭露層級

  1. 只在對話裡談生活情境與功能需求。
  2. 真實的血壓、三餐、體重只記錄在使用者自己手機的瀏覽器裡（localStorage）。
  3. 雙人同步只透過使用者主動打包、親自用 LINE 傳出去的一段連結，不經過任何第三方伺服器。
  4. 要不要把回診報告拿給醫師看，由使用者自己決定，AI 不會主動把資料送出去給任何人。

這次固定下來的界線

  • 血壓、三餐、留言、點菜等個人健康與生活資料，不落地到任何第三方伺服器或雲端資料庫。
  • 雙人同步只用「打包成一段文字連結」的方式，不使用即時雲端同步服務。
  • 完整備份檔案由使用者自己下載保管，AI 不會協助把備份上傳到任何外部服務。

第一部｜從需求到雙人健康工具上線完整紀錄

5. 先談方向，不先做細節

一開始我只要求「先列大綱跟方向，之後再討論細節」。AI 沒有直接動工，而是先給出七個生活面向的架構（飲食、運動、作息、監測、用藥、夫妻共同機制、壓力），並指出外食族最現實的限制——午晚餐在公司吃、菜色不能選——把飲食拆成「可控（早餐、宵夜、週末）」與「半可控（公司午晚餐）」兩層，再用五個具體問題收斂需求：早餐現況、宵夜習慣、家中設備、週末意願、先生動機。

6. 把回答變成可執行公式

我回答完五個問題後，AI 針對早餐、宵夜、週末三塊給出具體到「幾分鐘、用什麼設備、放什麼食材」的操作公式，而不是空泛的原則，並預告了網頁的技術路線：單檔 HTML、本機儲存、GitHub Pages。

7. 資料互通與角色設定

我提出三個關鍵要求：兩人資料要互通、且重點是我要看得到先生吃了什麼；風格要走我喜歡的小白熊（一二娟）／小棕熊（布布龍）路線；衛教要加重，因為先生的衛教觀念不足；食譜要分平日／假日、每餐多選項可替換。

8. 免伺服器同步機制的技術選型

AI 在動工前先確認一件事：雲端即時同步在這個情境下不必要，也不符合「本機不上雲」的隱私偏好，改採「打包成連結、用 LINE 互傳」的免伺服器同步機制（壓縮＋編碼），不需要我維運任何後端，也順便探勘了既有網站的系列／卡片慣例，確保新頁面能掛進「生活應用」系列。

9. 完整 v1 功能與端對端測試

AI 一次性做出完整第一版：熊的圖像、六項每日打卡、三餐記錄、對方今日卡片、平日／假日食譜、宵夜安全區、外食五招、十堂衛教問答、血壓趨勢圖、週回顧。這一輪用瀏覽器自動化模擬了先生打卡、產生同步連結、太太開啟連結、驗證資料正確帶入的完整流程，確認沒問題才推上工作分支，先只交付預覽檔，沒有直接上線。

10. 「我只是偷看模板還不能用嗎」：釐清預覽與上線的落差

我問了一句話，點出「預覽檔可以整套試玩，但不等於已經提供服務」的落差。AI 立刻釐清並在同一輪把工作分支合併進 main、推上線，同時提醒我記錄不會延續、要用正式網址重新開始。

做完功能、附上預覽檔，不代表使用者認知裡「東西已經可用」；上線與否要明確講清楚，不能讓使用者自己猜。

第二部｜互動、獎勵與資訊架構迭代完整紀錄

11. 從單向紀錄到雙向互動

我要的「互動感」很具體：先生看到想吃的菜，要能像敲碗一樣讓我知道。AI 設計了三個機制：收藏（⭐）、「我想吃這個」點菜板、印章式留言板＋自訂文字。

12. 3C 小白操作路徑收斂為兩步

先生是 3C 不熟悉的使用者，AI 刻意把他端的每一個互動都收斂成「點想要的東西 → 按一個大按鈕（現在傳或晚點傳）」，這個模式後來重複用在點菜、留言等每一個互動點，形成一致的操作語彙。

13. 資料保存疑問與三件套

我問到「定期檢視搜尋、跟醫生討論後續治療」，這把工具從習慣養成小物拉高到準醫療紀錄管理。AI 先誠實講清楚技術現實（本機儲存會一直留著，但有換機風險，不是雲端資料庫），再補上醫師報告（可列印存 PDF）、CSV 匯出（Excel 可搜尋篩選）、完整備份與還原三個功能。

14. 食譜可調整與自訂

同一輪我中途又補一句「食譜可能會調整」，AI 沒有等下一輪才處理，而是在同一次交付裡加上「我們的調整版」備註欄，並新增「我們的食譜」分頁讓兩人可以新增、修改、刪除自訂菜色，一併同步給對方。

15. 煙火獎勵三層次設計

我要「大大的獎勵」。AI 設計了三層次的煙火慶祝：單日達成、六項全滿、連續里程碑（3～100 天），並加上「對方也達成時我也會看到煙火」，把原本單向的自我打卡變成雙向的互相鼓勵。

16. 介面資訊架構三次收斂

這三輪是純粹的資訊架構調整：第一次是把攤開的頁面收成五條摺疊列；第二次是要求儀錶板不用點、直接顯示，其餘四項排成 2×2 方格；這兩輪的差異，反映我對「常看的資訊」與「偶爾查的資訊」有清楚的優先序，AI 跟著這個判斷微調，而不是自己猜一個布局就定案。

17. 底部導覽列密度調整

底部五個分頁鍵原本用滿版平均分散排列，圖示又偏小，容易被忽略。AI 改成置中群聚、放大圖示，解決了辨識度的問題。

18. 回顧頁月曆與色彩驗證

我要「一種顏色代表血壓、一種顏色代表打卡」的月曆點點檢視。AI 在動工前先用色彩驗證工具跑過候選配色，確認色盲安全與對比度都過關後才寫進頁面，並加上點一天看當日摘要的互動、月份翻頁、雙人切換。

第三部｜這次實際發生的偏航與修正

19. 把「附上預覽檔」當成「已提供服務」

AI 一開始把做完功能、附上預覽檔，等同於工作已經完成，沒有特別強調「這還沒上線」。

我的修正：一句「我只是偷看模板還不能用嗎？」點出這個落差。

可重複規則：任何時候只要還沒合併到正式版本，都要在交付訊息裡明講「這是預覽，還沒上線」，不能讓使用者自己猜測範疇。

20. 對「這個」和「工具集」的指涉想得太快

我問「這個應該放在工具集裡頭吧」時，AI 沒有直接猜「這個」指什麼，而是先想到這牽涉到我自己在 CLAUDE.md 訂過的嚴格收錄規則，兩者可能衝突。

AI 的處理：沒有自己決定要不要放寬規則，也沒有直接照做，而是先用結構化問題把「指的是什麼」與「規則衝突要怎麼處理」分開問清楚。

可重複規則：使用者的指示如果跟她自己先前訂下的明確規則有衝突，不要自己選邊站，要先攤開衝突、讓使用者自己決定。

21. 交付檔案沒有附上可以直接點的連結

AI 第一次交出兩份日誌檔案時，只講了檔案存放的相對路徑，沒有附上可以直接點擊的連結。

我的修正：提醒 AI 我早就講過「講做好了一定要附連結，不然我還要自己記資料夾」。

可重複規則：交付檔案的同一則訊息，一律同時附上可以直接點的連結（或直接傳送檔案本身），不能只講路徑或檔名。

22. 對連接器授權失敗重複硬試

嘗試連到 tarshar-vault（GitHub）與 Google Drive 搜尋工具時，反覆遇到「需要授權」的錯誤，但畫面上沒有真的跳出授權視窗。

我的修正：不再盲目重試同一個呼叫，改成誠實回報卡在哪一步、給出清楚的替代路徑（例如請使用者直接上傳檔案）。

可重複規則：同一個工具呼叫連續失敗且錯誤訊息沒有變化時，停止重試、誠實回報卡在哪裡，並提供使用者可以立刻執行的替代方案，而不是靠反覆嘗試碰運氣。

23. 找 schema 時先猜了 Notion，猜錯了

使用者要求「AI 協作日誌有固定 schema，去找一下」時，AI 先假設 schema 可能存在 Notion 資料庫裡，搜尋後找到「TAR 每日日誌」資料庫，但欄位結構跟真正的 schema 對不上。

我的修正：不是我來確認，而是最後直接把真正的範本檔案傳給 AI。

可重複規則：找不到明確吻合的東西時，要老實說「找到的是這個，但跟你要的可能對不上」，讓使用者判斷，而不是拿最接近的東西就當作答案交差。

24. 把一次同意延伸成之後每次都自動發佈

第一次合併上線有經過我明確同意，但從第二輪功能開始，AI 把這個同意延伸解讀成之後每一版做完都可以直接合併進 main、只回報「上線了」。

目前我沒有反對這個做法，但這是 AI 自己延伸出來的默契，不是我每次都重新答應的。

可重複規則：即使先前有過一次同意，涉及「公開發佈」這類會被別人看到的動作，最好還是每次都用一句話讓使用者知道要發佈了，不能假設同意會自動延續到未來每一次；如果使用者從未表示反對，也應該在類似這樣的紀錄裡誠實寫下來，而不是視為理所當然。

第四部｜這次的正式決策帳

25. 已確認決策

編號決策為什麼
01用本機儲存＋連結傳輸做雙人同步，不用雲端伺服器保留「本機不上雲」的隱私偏好，且不需要維運後端
02網頁上線前一律先在工作分支交付預覽，經明確同意才合併 main避免「做完＝已上線」的認知落差
03儀錶板常駐顯示、其餘四功能收成 2×2 方格實際用過後發現全部攤開容易被忽略，改為漸進揭露
04底部導覽列改置中群聚並放大圖示原本平均分散造成圖示分散、辨識度低
05打卡血壓日曆用綠／藍兩色點點，且先跑色彩驗證工具才定案確保色盲、色弱的人也能分辨兩種資訊
06先生端所有互動操作收斂成「點選項→按一個大按鈕」兩步對象是 3C 不熟悉的使用者，操作路徑要盡量少
07每次改版前先用瀏覽器自動化模擬雙人打卡、同步、互動流程再交付避免同步或煙火邏輯出錯要等使用者發現才知道
08醫師報告、CSV、備份三個功能一次補齊，不是只做字面上被要求的那一項對應「還要跟醫生討論」這個更大的真實需求
09這次的協作日誌與學習日誌採事後補寫使用者是先看到成果滿意後才要求記錄過程，跟先寫日誌再動工的順序不同
10家人健康敏感資料一律不落地到任何第三方伺服器呼應使用者對隱私的明確重視

第五部｜學習關鍵字辭典

26. 協作與流程

localStorage｜瀏覽器本機儲存

  • 白話：資料只存在這支裝置的瀏覽器裡，不會自動送到任何伺服器。
  • 本案例子：小熊健康小屋的打卡、血壓、留言全部存在使用者自己手機的瀏覽器裡。

Feature Branch｜功能分支

  • 白話：新功能先在一個獨立的分支上開發，確認沒問題才合併進正式版本。
  • 本案例子：每次修改都先推到工作分支，經使用者明確說「上線」才合併進 main。

End-to-End Test｜端對端測試

  • 白話：模擬真實使用情境從頭到尾走一遍，而不是只看程式碼本身有沒有錯字。
  • 本案例子：每次改版都用瀏覽器自動化模擬先生打卡、傳連結、太太收到同步，確認資料和畫面都對才交付。

Serverless Sync｜免伺服器同步

  • 白話：兩端資料交換不透過中間的伺服器，而是把資料包進一段文字（連結），由使用者自己傳遞。
  • 本案例子：用壓縮＋編碼把兩人的紀錄包進 LINE 連結，對方點開才寫入自己的手機。

27. 設計與隱私

Progressive Disclosure｜漸進式揭露

  • 白話：先只顯示最重要的資訊，其餘的點了才展開，避免一次塞太多東西。
  • 本案例子：今日頁從「全部攤開」改成「儀錶板常駐＋其餘四項收成 2×2 方格，點了才展開」。

Color-Vision-Deficiency Safe Palette｜色盲安全配色

  • 白話：選顏色時要驗證色盲、色弱的人是否也分得清楚，不能只靠設計者自己的眼睛判斷。
  • 本案例子：日曆的打卡／血壓兩色點點，先用色彩驗證工具跑過才定案。

Tacit Knowledge Externalization｜隱性知識外化

  • 白話：把一個人心裡沒明說、憑經驗判斷的東西，講清楚變成別人也能照著做的具體規則。
  • 本案例子：使用者對「食物怎麼吃比較健康」「什麼時候該給獎勵」的直覺，被一步步問出來變成飲食公式、煙火觸發規則等可執行規格。
